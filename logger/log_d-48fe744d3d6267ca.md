# Constant-rate timing exceeds the maximum allowed drift

Product: Nimble Streamer
Component: MPEG-TS transport input and output
Logging function: log_d
Log level: debug
Documentation ID: log_d-48fe744d3d6267ca

## Log pattern

```text
max_mux_delay reached for [%s:%d] offset=%lld initial_dts=%lld last_dts=%lld mux_rate=%lld mux_delay=%lld max_mux_delay=%lld
```

## Parameters

- Argument 1 — Destination: Configured destination IP address.
- Argument 2 — Port: Configured destination port.
- Argument 3 — Byte offset: Transport bytes produced since the current constant-rate timing origin.
- Argument 4 — Initial DTS: Timing origin in 90 kHz ticks.
- Argument 5 — Last DTS: Most recent media decoding timestamp in 90 kHz ticks.
- Argument 6 — Mux rate: Configured rate in kilobits per second.
- Argument 7 — Mux delay: Configured normal delay threshold in milliseconds.
- Argument 8 — Maximum mux delay: Configured timing reset threshold in milliseconds.

## Log examples

Illustrative examples; these are not captured server logs.

```text
max_mux_delay reached for [192.0.2.20:5000] offset=1316000 initial_dts=90000 last_dts=900000 mux_rate=4000 mux_delay=100 max_mux_delay=1000
```

## Short description

Constant-rate timing exceeds the maximum allowed drift.

## Trigger condition

The absolute difference between the latest media DTS and the byte-count-derived constant-rate DTS reaches the configured maximum mux delay.

## Explanation

The byte offset is reset, the initial DTS is moved to the latest DTS, and per-stream last-PCR times are cleared so timing can restart.

## Possible causes

- The absolute difference between the latest media DTS and the byte-count-derived constant-rate DTS reaches the configured maximum mux delay.

## What to check

1. Compare media timestamp continuity, mux rate, and calculated elapsed output time.

## Recommended action

Correct unexpected timestamp jumps or an unsuitable mux rate.
